[#workingwiththeisolatedbespokefirmware]
=== Working with the isolated, bespoke firmware

To avoid disturbing the working QMK tree used by my other QMK-Vial keyboards,
and because there are other specific settings incongruous with the latest
`qmk_firmware` repository, `qmk_firmware_Rev.2.5-2U.zip` should be extracted
into a separate, isolated directory, for example,
`/c/Users/kenny/qmk_firmware_geonix40`.  Then `qmk config user.qmk_home` must
be pointed at that isolated directory for the duration of compiling the
Geonix’s `.bin` file.  This command, presuming the current working directory is
`qmk_firmware_geonix40`, noted above, will achieve that:

[source,shell-session]
----
qmk config user.qmk_home="$(pwd)"
----

It persists across sessions, so needs explicit reversion later, to ensure other
non-bespoke builds work (which is easy to forget):

[source,shell-session]
----
qmk config user.qmk_home="$HOME/qmk_firmware"
----

[#amplefirmwarememorylimitedeeprom]
=== Ample firmware memory, limited EEPROM

Unlike my KPRepublic BM40’s ATmega32U4, the memory cost of per-key,
brightness-reactive RGB lighting is incidental on the Geonix given its
ES32FS026 MCU, which has 128 kB of flash memory.  My final build only amounts
to around 62 kB, so there is ample flash memory available on this keyboard.

ifdef::env-codeberg[&#x00A0; ]

Where the ES32FS026 MCU is less endowed is EEPROM memory.  Its `EEPROM_SIZE` is
1152 bytes, backed by the vendor’s own custom flash-emulated scheme
(`EEPROM_CUSTOM = custom`, with its own `FEE_PAGE_SIZE`, `FEE_PAGE_COUNT`, and
`FEE_PAGE_BASE_ADDRESS` settings in the stock’s `keymaps/vial/config.h`), not
QMK's own wear-levelling driver.

ifdef::env-codeberg[&#x00A0; ]

[NOTE]
====
The consequence of this is that there is a low ceiling for any EEPROM-consuming
features’ settings.  However, in my case, with the BM40 having only 1024 bytes
– _see its_
ifndef::env-codeberg,env-github[xref:../bm40/README#workingwithalimitedfirmwaresizeceiling[README]]
ifdef::env-codeberg,env-github[link:../bm40/README.adoc#workingwithalimitedfirmwaresizeceiling[README]]
– the common settings across my boards “fit” fine.  This is observational, not
measured; however, it makes sense given the 128 bytes more memory on the
Geonix.  I measured the BM40’s ceiling precisely, but never ran the same tests
for Geonix, so its exact available surplus is interpolated as at that amount of
available space.  The consequence is, it would only be if numbers of things
like layers (particularly), combos, and other things that consume EEPROM were
added, that the Geonix’s ceiling would be reached quickly.  The flip side is
that the 1152 bytes appears to be a low, self-imposed ceiling rather than a
hard limit.  Calculating from
<<filegeonix40keymapskennypeteconfigh,keymaps/kennypete/config.h>>'s values:
`FEE_PAGE_SIZE` (512) × `FEE_PAGE_COUNT` (8) = 4,096 bytes, which exactly
matches `FEE_MCU_FLASH_SIZE` (0x1000).  This confirms that’s the raw flash
reserved for the scheme.  `FEE_PAGE_BASE_ADDRESS` (0x1F000) sitting at the
start of the last 4 kB of the 128 kB ES32FS026 chip, and ending precisely at
its top.  Only 1152 of those 4096 raw bytes become usable EEPROM, a roughly
3.5x overhead.  Of course, this needs to be considered only by someone wanting
to use my `kennypete` build as a base for their own layout, combos, etc.,
though it appears an increase in the `EEPROM_SIZE` is feasible, if it’s wanted.
====

[#startingpoint]
=== Starting point

Unlike my other boards, the Geonix does not build from mainline qmk_firmware.
As noted  <<workingwiththeisolatedbespokefirmware,above>>, the starting point
is Chosfox’s source `.zip`.  Importantly, a meaningful component is the
vendor's `rdr_common.c`, which is not present in that source.  Instead, its
precompiled object is only available inside `librdrcommon.a`, and how that
works is opaque.

ifdef::env-codeberg[&#x00A0; ]

In that context, what follows is more detailed than the documentation of my
other boards’ setups.  Whereas they are mostly configuration and ensuring
feature-parity, this setup addresses other things, including some bugs (both in
the vendor’s fork and one in the point-in-time QMK code).  Further, in some
places, the vendor’s code was found to be incompatible to call outside the
stock setup.  That required functionality to be built, not ported.  Such things
are flagged in this documentation in each applicable file’s explanation.

[#chconfh]
==== chconf.h

This is a board-specific low-level timer configuration for the ES32FS026.  It
remains unchanged.

[#confighamendments]
==== config.h amendments

This file is changed significantly, though only to remove redundant content.

* `LOCKING_SUPPORT_ENABLE` and `LOCKING_RESYNC_ENABLE` are removed.
There is no compiled-in default anywhere in QMK core, and no lock-switch on
this board (being a Choc-switch, low-profile keyboard), and testing found no
issues removing these.
* `FORCE_NKRO` and all related comments are removed.
This is entirely commented anyway, so removing it is simply cleaning up of a
needless no-op comment block.
* `DEBOUNCE 5` is removed as it is redundant.
Directly checking the source reveals `quantum/debounce/asym_eager_defer_pk.c`
(Geonix's actual debounce algorithm) falls back to exactly 5 when not
overridden so removing it changes nothing.
* `NOP_FUDGE 0.4` is removed.
This constant only feeds `CYCLES_PER_SEC` inside
`platforms/chibios/drivers/ws2812_bitbang.c`, the software bit-banged WS2812
driver, and Geonix never uses that file at all.  Its RGB output goes through
the vendor's dedicated PWM+DMA hardware path
(`g_es_pwm_rgb_matrix_array_dma_buf`, confirmed in `rdr_common.h`), which is a
different mechanism.  Also it is absent from every compile log, corroborating
the source code findings.
* `RGB_MATRIX_LED_FLUSH_LIMIT 16` and `RGB_MATRIX_VAL_STEP 16` are removed.
Both are flagged by qmk lint as redundantly matching QMK’s documented defaults,
like `DEBOUNCE`.
* Chinese comments are translated to English; no CJK characters remain.
* `RGB_MATRIX_LED_COUNT 76` is kept as it is a correct constant (47 real
keys + 29 logo-strip LEDs) and changing this would misalign every LED’s data.
* `RGB_MATRIX_FRAMEBUFFER_EFFECTS` is kept, though is possibly
redundant (because I do not believe the `kennypete` ever invokes QMK's
framebuffer effects).

The net result is every functional line is unchanged and everything removed was
proven inert (in at least one of: the source code; lint; already
commented-out).

ifdef::env-codeberg[&#x00A0; ]

The file also is in plain English now, with per-line comments explaining intent
rather than the stock’s less helpful annotations (for a monolingual English
speaker like me).

[#geonix40camendments]
==== geonix40.c amendments

This is another file with significant changes, especially the RGB-handling
removals and additions:

* The stock `bool rgb_matrix_indicators_advanced_user()`, which
calls the vendor’s `User_Led_Show()`, is removed.  That function proved
incompatible on my remapped layout (e.g., its `Key_Fn_Status` global assumes Fn
sits at a stock matrix position now occupied by `TD(2)`).  Per-key RGB is
included in <<keymapskennypetekeymapcamendments,keymaps/kennypete/keymap.c>>,
using functions common to my 40&#x0025; keyboards (i.e., a CSTC40 and two
BM40s).
* `process_record_user()` is deleted from the end of the stock file and
moves, in an amended form, to after the RGB initialisation section, and is
extended to intercept `RGB_RTOG`, toggling a new `rgb_layer3_always_on` flag
rather than falling through to the vendor’s handling.  This keeps layer 3’s
status display visible even when the main RGB Matrix is otherwise toggled off.
* Matrix/position/flags arrays in `g_led_config` are unchanged except
for being reformatted and commented clearly (e.g., the `(3,1)` gap and the
47-key/29-logo-strip split being explained inline).
* All Chinese comments are translated to English and section headers and
formatting are tidied.

[#halconfhamendments]
==== halconf.h amendments

The stock file’s `BACKLIGHT_PWM_DRIVER` and `BACKLIGHT_PWM_CHANNEL` lines are
deleted.  They are unnecessary because they relate to QMK’s traditional
single-colour backlight feature, which is not enabled on the Geonix where
per-key RGB Matrix is used instead.  I confirmed this by an unchanged compile
(i.e., byte-identical object files) and no source references to them.

ifdef::env-codeberg[&#x00A0; ]

What’s retained is the four `TRUE` lines: `HAL_USE_PWM`,
`ES32_PWM_USE_GP16C4T2`, `HAL_USE_USB`, and `HAL_USE_PAL`.  Testing revealed
these drive changes to `hal.o`, `hal_pwm.o`, and `hal_pwm_lld.o`, consistent
with these settings being related to RGB (PWM timer selection), USB, and GPIO
respectively, and whether any, or even all, of these lines are strictly
necessary is something that was not delved into further.

[#keyboardjsonamendments]
==== keyboard.json amendments

This file defines the board itself, i.e., matrix pins, USB IDs, QMK features
available by default (other than what is in `keymaps/kennypete/rules.mk`, and
the RGB Matrix hardware layout).

ifdef::env-codeberg[&#x00A0; ]

Changes made:

* `"consolekey": true` is removed from `features` because it does nothing;
it does not match any real QMK `features` schema key (the closest real key is
`console`).
* `command: false` is the `COMMAND_ENABLE` default, so it is removed,
though is included in `rules.mk` as `COMMAND_ENABLE = no` and commented there.
* `usb` and `matrix_pins` are moved (without any value changes), simply
to match the field ordering used in my other boards’ `keyboard.json` files.
* `nkro` remains `true` in `features` because it is required to satisfy a
dependency in `librdrcommon.a`, but a new
`"host": {"default": {"nkro": false}}` block is added, forcing 6KRO by default
at runtime, matching my other boards.
* `rgb_matrix.animations` is reduced from 49 available effects down to
just three (`cycle_all`, `cycle_left_right`, and `hue_pendulum`).  As I have no
desire for more than a few animations, usually preferring "Direct Control" with
my per-key solid colours, this is for personal preference and alignment rather
than a space-saving measure.
* The layout is fundamentally corrected.  The stock `keyboard.json` defined
it as `LAYOUT_tkl_ansi`, with staggered coordinates (fractional `y` offsets, a
`w: 1.25` key), which would be fine for a TKL/ANSI-style layout, but with the
Geonix being a 40% ortholinear board, it is inappropriate.  It is renamed
`LAYOUT_ortho_4x12_1x2uC` (matching my other 40&#x0025;) with integer
coordinates and the single 2u key correctly declared as `w: 2`.

[NOTE]
====
This file’s `features` block also sets `mousekey`, `extrakey`, and `rgb_matrix`
to true, which are not just incidental for my setup because the:

* mouse keys on Layer 5 depend on `mousekey` being enabled,
* the media/volume row requires `extrakey`, and
* the per-key RGB system needs `rgb_matrix`.

These three enabled settings then cascade (forced by QMK core code), setting:

* `MOUSEKEY_ENABLE = true`, which sets `MOUSE_ENABLE` as
enabled (in `builddefs/common_features.mk`)
* `MOUSE_ENABLE` and `EXTRAKEY_ENABLE` each independently force
`SHARED_EP_ENABLE` on (in `tmk_core/protocol.mk`).
====

[#mcuconfhamendments]
==== mcuconf.h amendments

This file is reduced to a single comment, with no remaining executable content
&#x2013; not even `#pragma once` &#x2013; because double-inclusion is n/a.  The
stock file’s only real content, `#define ES32_USB_USE_USB0 TURE` (noting the
inexplicable `TURE` typo) and an
already-commented-out `#include_next <mcuconf.h>`, were essentially worthless.

ifdef::env-codeberg[&#x00A0; ]

Testing confirmed `mcuconf.h` file simply must _exist_: QMK's ChibiOS config,
`platforms/chibios/boards/common/configs/halconf.h`, has
`#include <mcuconf.h>`, regardless of the board.  With the file absent
entirely, the compile fails
with `fatal error: mcuconf.h: No such file or directory`; with the file present
but reduced to a comment only, it compiles fine.

[#rulesmkamendments]
==== rules.mk amendments

This is the board-level file, not the one in `keymaps/kennypete`.
QMK-recognised "processor" values (such as my BM40’s ATmega32U4 and my CSTC40’s
STM32F401), are already known in QMK’s build system, so the low-level
parameters set in the Geonix’s `rules.mk` must be explicitly stated for its
ES32FS026.

ifdef::env-codeberg[&#x00A0; ]

Consequently, the file is left mostly as-is, but for two lines:

* `EEPROM_CUSTOM = custom`, which is removed because it is effectively inert.
The file `qmk_firmware/builddefs/common_features.mk` tests the variable
`EEPROM_DRIVER`, not `EEPROM_CUSTOM`.  So the current line set a Makefile
variable that is not read.  The Geonix’s driver selection, `EEPROM_DRIVER =
custom`, is in `keymaps/kennypete/rules.mk`, which is unaffected by this
removal.
* With no rotary encoders on the physical board, `ENCODER_MAP_ENABLE = yes` is
redundant and is removed.

[NOTE]
====
`BLUETOOTH_CUSTOM = yes` is retained, though evidence suggests that it is
redundant.  That is because no `BLUE*` setting appears in either the stock or
my build’s <<featureslist,cflags.txt>>, and a dump of the vendor’s precompiled
`librdrcommon.a` (using `nm`) shows its wireless handling is self-contained
(i.e., 2.4G and BLE both) with no reference to anything Bluetooth-flag-related.
Since that archive is compiled by the vendor and never sees this build’s
`rules.mk`, it is unaffected by this line.  However, removing it does change
two compiled files (`via.o` and `quantum/keymap_introspection.o`), but
presumably that is simply reflecting those files’ changing with _any_
`rules.mk` edit.  I did not retest BLE pairing/reconnection after temporarily
removing it, though someone else may want to dive into this to definitively
determine whether it is redundant or has some latent purpose.  So, that is why
`BLUETOOTH_CUSTOM = yes` is retained.
====

Vial’s unique board identifier and unlock key combination, how many layers
Vial’s dynamic keymap supports, and so on.

ifdef::env-codeberg[&#x00A0; ]

The following are changed:

ifdef::env-codeberg[&#x00A0; ]

|===
^.^m|VIAL_UNLOCK_COMBO_ROWS <.^| The unlock keys’ rows are standardised to the

[#keymapskennypetekeymapcamendments]
==== keymaps/kennypete/keymap.c amendments

As its filename suggests, <<filegeonix40keymapskennypetekeymapc,keymap.c>>
contains QMK’s keymap for the board when it is compiled.  Unlike with my
CSTC40, this is not a verbatim copy of the BM40’s file.  The underlying per-key
colour mechanism _is_ reused directly, but the layout itself (Layer 3
specifically) is different, reflecting the Geonix Rev.2.5’s hardware and vendor
requirements.

* *Includes*: `"../../../lib/lib8tion/lib8tion.h"` is added.
It is required for `sin8()`, the function driving the replacement pairing-pulse
effect (see <<geonix40camendments,geonix40.c amendments>>) in
`rgb_matrix_indicators_user()`.
`QMK_KEYBOARD_H` is standard boilerplate present on every keymap;
`"../../../lib/rdr_lib/rdr_common.h"` is stock, providing the `MD_*` &#x002F;
`QK_BAT` declarations this file uses.
* *Layout macro*:
The stock file used `LAYOUT_tkl_ansi`, a genuinely staggered layout definition
ill-suited to this ortholinear 40% board (see
<<keyboardjsonamendments,keyboard.json amendments>>).  It is replaced with
`LAYOUT_ortho_4x12_1x2uC`, matching my other boards.
* *Encoder map*:
The stock file’s `#if defined(ENCODER_MAP_ENABLE)` block, mapping two physical
rotary encoders to volume/RGB controls, is removed.  The Geonix has no rotary
encoders (see <<rulesmkamendments,rules.mk amendments>>, where
`ENCODER_MAP_ENABLE` is similarly removed as it is redundant).
* *Layers 0-2* (`_BASE`, `_SYMBOLS`, `_NUMBERS`): These are reworked the same
way as my other boards, aligning the default, pre-Vial state reasonably closely
with my actual Vial layout, so common typing tasks work correctly for me even
before the `.vil` file is loaded.footnote:[As with the BM40/CSTC40, there is some inherent, harmless deception here: several keys on layers 1 and 2 remain `KC_NO` colour-wise rather than their eventual Vial-assigned state, with no meaningful consequence.]
For the general rationale behind this approach, see the BM40’s
ifndef::env-codeberg,env-github[xref:../bm40/README#keymapskennypetekeymapcamendments[README].]
ifdef::env-codeberg,env-github[link:../bm40/README.adoc#keymapskennypetekeymapcamendments[README].]
* *Layer 3* (`_ADJUST`) is very different from my other boards’
equivalents, and not just cosmetically.  Rather than a bare Reset-only layer,
this one combines Reset, `U_EE_CLR` (EEPROM clear), the Geonix’s wireless
input-source selectors (`MD_USB`, `MD_BLE1`, `MD_BLE2`, `MD_BLE3`, and
`MD_24G`), and battery query (`QK_BAT`), which is functionality this board
needs and the others don’t have.  This layer’s specific always-on RGB behaviour
(independent of the general RGB toggle) is already explained in
<<geonix40camendments,geonix40.c amendments>>, alongside the `RGB_RTOG`
interception and `rgb_layer3_always_on` flag that drive it.
+
The `rgb_matrix_indicators_user()` function replaces only the *display* of
status.  That is, which LED shows which colour, for wireless mode and battery
level, specifically superseding three vendor functions still present in
`librdrcommon.a` but no longer called anywhere (i.e., `User_Led_Show()`,
`Led_Batt_Number_Show()`, and `Led_Rf_Mode_Show()`).  Previously, these were
invoked via the (now-deleted) `rgb_matrix_indicators_advanced_user()` in
`geonix40.c`.  It does *not* replace the underlying logic those displays were
reporting on: wireless mode switching, actual battery-level detection, and
keycode dispatch for everything else remains entirely vendor-driven via
`Key_Value_Dispose()`, which is still called for every keycode _except_
`RGB_RTOG` (see <<geonix40camendments,geonix40.c amendments>>).  Layer 3
supplies the keys that trigger these mechanisms; it does not reimplement the
mechanisms themselves.
* *Per-key colours*: the entire mechanism (`apply_hsv_table()` &#x002F;
`apply_off_table()`, the `RC(row, col)` packing macro, and the 14 `HS_*`
hue/saturation definitions) is reused directly from my BM40’s `keymap.c`,
unchanged.  For the full explanation of why colours are stored as
hue/saturation pairs rather than full RGB, how brightness is read live rather
than stored (so fixed colours respond to `Bright+` &#x002F; `Bright-`, and the
RGB-to-HSV derivation worked through for three of the palette's colours, see
the BM40's
ifndef::env-codeberg,env-github[xref:../bm40/README#keymapskennypetekeymapcamendments[README].]
ifdef::env-codeberg,env-github[link:../bm40/README.adoc#keymapskennypetekeymapcamendments[README].]
+
Layer 3 is different, however.  `Reset` and `U_EE_CLR` keys are
fixed-brightness red, i.e., the same safety-indicator rationale as I use on the
BM40/CSTC40, but, further, this layer's *entire* rendering path bypasses the
normal brightness-scaling logic per the `rgb_layer3_always_on` mechanism
already covered above.  That makes sense because the point of the source
indicators and battery level indicator is **to be visible**!
+
NOTE: The final presentation of this RGB per-key setup is shown in the six
photos at <<keyboardphotos,Keyboard photos>>.

[#keymapskennypetevialjsonamendments]
==== keymaps/kennypete/vial.json amendments

The file <<filegeonix40keymapskennypetevialjson,vial.json>> is Vial’s
descriptor for the board, including physical key layout, matrix dimensions, and
it also determines which optional Vial-specific GUI features to expose.

ifdef::env-codeberg[&#x00A0; ]

There are several changes made to this file:

* The following VIA-only
metadatafootnote:[“`name`, `vendorId`, `productId`: while these options are required by VIA, Vial does not need them. You do not have to add them, and even if you do, their contents will not be used.” - https://get.vial.today/docs/porting-to-via.html#2-create-a-json-containing-the-full-keyboard-definition]
is removed:
+
[source,json]
----
	"name": "GEONIX REV.2.5",
	"vendorId": "0x36B0",
	"productId": "0x313B",
----
* `customKeycodes` is reduced from 26 entries to 10, purging everything
from `USER_CH` onwards.  The reason is I do not use any of them, so they are
needless distractions in Vial, and their omission means none are presented as
pickable Vial codes:
** `USER_CH`, "Switch F area and Num area";
** `QK_DEB`, "Number of times that the key shakes off";
** `KbPrSlp`, "Keyboard primary sleep";
** `KbdSecS`, "Keyboard secondary sleep";
** `TEST`, "Test Keyboard Colour";
** `LG_*`, Various logo lighting keycodes ("Toggle logo lighting on or off",
"Cycle through modes", "Cycle through modes in reverse", "logo Increase hue",
"logo Decrease hue", "logo Increase saturation", "logo Decrease saturation",
"logo Increase value (brightness)", "logo Decrease value (brightness)", "logo
Increase effect speed", and "logo Decrease effect speed").
* The `layouts.keymap` block is stripped of all KLE-style visual
metadata.  The stock `vial.JSON` (_note the odd capitalisation too),
indicatively has the `"Key Color"` (`"c"`) KLE property specified for some keys,
but although Vial’s porting documentation describes first designing a physical
layout in real KLE, I do not believe that some properties are honoured by Vial.
I tested (`"c"`, `"f"`, and `"t"`) and none appeared to do anything in Vial,
regardless of theme, and on both Windows and Linux (with versions 0.7.1 and
0.7.5).  Conversely, `w` does work, with the 2U key presented correctly.  The
stock file’s `"c"` values are plausibly an afterthought of the original KLE
design session, carried through unedited when legends were swapped for matrix
coordinates.  Accordingly, the `"c"` components are removed, reducing the
keymap to bare matrix-position strings, which is kind of convenient as it
matches my BM40 and CSTC40 `vial.json` files, though with different row 3
positions.
* Mixed tabs and spaces issues are addressed with a consistent 4-space
indent.

[NOTE]
====
I do not use `QK_WLO`, and `SIX_N` cannot be used because I disable NKRO.
Regardless, both are retained rather than removed.  That is because each
`customKeycodes` entry’s actual keycode value is determined by its position in
the array.  Removing entries from the end leaves every remaining entry’s index,
and therefore its keycode, unchanged.  Removing from the middle would shift
every subsequent entry’s index down by one, silently reassigning a different
keycode to each (and corrupting anything already configured to use them).
Consequently, only the contiguous set of `customKeycodes` from 11 to 26
(inclusive) are removed.
====

    if (Keyboard_Info.Key_Mode == QMK_USB_MODE) {
        if (usb_device_state.configure_state == USB_DEVICE_STATE_CONFIGURED) {
            if (!usb_enum_done) {  // Only execute on the first CONFIGURED event

                Usb_If_Ok_Led = true;
                Usb_If_Ok_Delay = 0;

            usb_enum_done = false;  // Reset on disconnect
        }

    }

#define RC(r, c) (((r) << 4) | (c))

static void apply_hsv_table(const uint8_t (*table)[3], uint8_t count) {
    uint8_t val = rgb_matrix_get_val();  // live global brightness

    for (uint8_t i = 0; i < count; i++) {
        uint8_t rc  = pgm_read_byte(&table[i][0]);
        uint8_t h   = pgm_read_byte(&table[i][1]);
        uint8_t s   = pgm_read_byte(&table[i][2]);
        uint8_t row = rc >> 4;
        uint8_t col = rc & 0x0F;

        HSV hsv = {h, s, val};
        RGB rgb = hsv_to_rgb(hsv);

        uint8_t led_index = g_led_config.matrix_co[row][col];
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, rgb.r, rgb.g, rgb.b);
        }
    }
}

static void apply_off_table(const uint8_t *table, uint8_t count) {
    for (uint8_t i = 0; i < count; i++) {
        uint8_t rc  = pgm_read_byte(&table[i]);
        uint8_t row = rc >> 4;
        uint8_t col = rc & 0x0F;
        uint8_t led_index = g_led_config.matrix_co[row][col];
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_OFF);
        }
    }
}

// Hue, Sat pairs for colour names
//
// QMK's RGB Matrix works in HSV internally, scaled 0-255 for all three of
// H/S/V (not the usual 0-360 degrees / 0-100% you'd see in a colour picker).
// Only H and S are stored here; V comes from the current brightness at
// render time, which is what makes these colours respond to Bright +/-.
//
// RGB->HSV conversion, worked for all three possible "max channel" cases
// (the hue formula changes depending on which of R/G/B is largest):
//
// R is max -- "MAGENTA" RGB (255, 0, 126):
//   max=255 (Red), min=0, delta=255
//   S = 255 * (delta/max) = 255 * (255/255) = 255
//   H = 60 * ((G-B)/delta) = 60 * ((0-126)/255) = -29.65 deg
//   Negative result -- wrap by adding 360: -29.65 + 360 = 330.35 deg
//   H rescaled to QMK's 0-255: round(330.35 * 255/360) = 234
//   -> HS_MAGENTA = 234, 255
//
// G is max -- "GREEN" RGB (0, 255, 0):
//   max=255 (Green), min=0, delta=255
//   S = 255 * (delta/max) = 255 * (255/255) = 255
//   H = 60 * (((B-R)/delta) + 2) = 60 * (((0-0)/255) + 2) = 120 deg
//   H rescaled to QMK's 0-255: round(120 * 255/360) = 85
//   -> HS_GREEN = 85, 255
//
// B is max -- "ROYAL" RGB (83, 184, 255):
//   max=255 (Blue), min=83, delta=172              <- not fully saturated;
//                                                      min isn't 0 here
//   S = 255 * (delta/max) = 255 * (172/255) = 172
//   H = 60 * (((R-G)/delta) + 4) = 60 * (((83-184)/172) + 4) = 204.77 deg
//   H rescaled to QMK's 0-255: round(204.77 * 255/360) = 145
//   -> HS_ROYAL = 145, 172
//
// V (brightness) is always just the max channel itself, unscaled -- but it's
// deliberately not stored in these pairs, since it comes live from the
// board's current brightness setting instead (see apply_hsv_table above).
//
// Hue, Sat pairs for the built-in RGB_* colours (quantum/colors.h) with
// lime bespoke to ensure it is visually distinct and not quasi white
#define HS_WHITE     0,   0
#define HS_ROSE      0,   90
#define HS_RED       0,   255
#define HS_ORANGE    24,  150
#define HS_YELLOW    42,  255
#define HS_LIME      68,  167
#define HS_GREEN     85,  255
#define HS_EMERALD   107, 255
#define HS_CYAN      128, 255
#define HS_ROYAL     145, 172
#define HS_BLUE      170, 255
#define HS_PURPLE    190, 172
#define HS_PINK      212, 255
#define HS_MAGENTA   234, 255

extern bool rgb_layer3_always_on;  // (geonix40.c has layer 3 RGB always on)

bool rgb_matrix_indicators_user(void) {
    uint8_t layer = get_highest_layer(layer_state);

    /* Special treatment of layer three, which has the QK_BOOT key, Connection
       and Battery selectors and indicators.  The RGB for this layer should
       be always on as it only has things that are shown in LEDs and the
       potentially dangerous QK_BOOT key!  Fixed-brightness for the selector
       keys and the indicators is fine also.  The QK_BOOT (0,4) and EEPROM
       clear (0,3) keys are made red, and on their own line (row 0).       */

    if (!rgb_layer3_always_on && layer != 3) {
        rgb_matrix_set_color_all(RGB_OFF);
        return false;
    }

    if (layer == 3) {
        rgb_matrix_set_color_all(RGB_OFF);

        uint8_t led_index = g_led_config.matrix_co[0][3];  // U_EE_CLR
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_RED);
        }

        led_index = g_led_config.matrix_co[0][4];          // QK_BOOT
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_RED);
        }

        led_index = g_led_config.matrix_co[2][0];          // USB
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_AZURE);
        }

        led_index = g_led_config.matrix_co[2][1];          // BLE1
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_BLUE);
        }

        led_index = g_led_config.matrix_co[2][2];          // BLE2
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_BLUE);
        }

        led_index = g_led_config.matrix_co[2][3];          // BLE3
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_BLUE);
        }

        led_index = g_led_config.matrix_co[2][4];          // 2.4G
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_TEAL);
        }

        led_index = g_led_config.matrix_co[2][7];          // BAT
        if (led_index != NO_LED) {
            // TBD whether this is needed.  The battery indicator will
            // display, though this should force it.  It's not given a
            // colour because of that reason (plus the battery indicator
            // is cleaner / does not bleed together with this key if it
            // is kept as black.
            rgb_matrix_set_color(led_index, RGB_BLACK);
        }

        led_index = g_led_config.matrix_co[3][5];          // Lower being held
        if (led_index != NO_LED) {
            // Retained only so if someone does want to have a colour on this
            // key it is easy to alter with RGB_{valid_option_per_colors.h}
            rgb_matrix_set_color(led_index, RGB_BLACK);
        }

        led_index = g_led_config.matrix_co[3][7];          // Raise being held
        if (led_index != NO_LED) {
            // Retained only so if someone does want to have a colour on this
            // key it is easy to alter with RGB_{valid_option_per_colors.h}
            rgb_matrix_set_color(led_index, RGB_BLACK);
        }

        // Row 1: live status indicators, read directly from Keyboard_Info
        // (the one extern struct in rdr_common.h); no vendor function calls
        // are involved, so none of the Led_*_Show() breakage risk persists,
        // noting retaining anything to do with RGB lighting caused dire
        // per-key RGB impacts.

        // Which of USB / BLE1-3 / 2.4G is active at present: exactly one
        // lights up, matching row 2's selection
        led_index = g_led_config.matrix_co[1][0];  // USB active?
        if (led_index != NO_LED && Keyboard_Info.Key_Mode == QMK_USB_MODE) {
            rgb_matrix_set_color(led_index, RGB_WHITE);
        }

        led_index = g_led_config.matrix_co[1][1];  // BLE1 active/pairing?
        if (led_index != NO_LED && Keyboard_Info.Key_Mode == QMK_BLE_MODE
            && Keyboard_Info.Ble_Channel == QMK_BLE_CHANNEL_1) {
            if (Keyboard_Status.System_Connect_Status == KB_MODE_CONNECT_PAIR) {
                uint8_t breath = sin8(timer_read() >> 2);
                HSV hsv = {170, 255, breath};      // blue hue, pulsing
                RGB rgb = hsv_to_rgb(hsv);
                rgb_matrix_set_color(led_index, rgb.r, rgb.g, rgb.b);
            } else {
                rgb_matrix_set_color(led_index, RGB_WHITE);  // steady once connected
            }
        }

        led_index = g_led_config.matrix_co[1][2];  // BLE2 active/pairing?
        if (led_index != NO_LED && Keyboard_Info.Key_Mode == QMK_BLE_MODE
            && Keyboard_Info.Ble_Channel == QMK_BLE_CHANNEL_2) {
            if (Keyboard_Status.System_Connect_Status == KB_MODE_CONNECT_PAIR) {
                uint8_t breath = sin8(timer_read() >> 2);
                HSV hsv = {170, 255, breath};      // blue hue, pulsing
                RGB rgb = hsv_to_rgb(hsv);
                rgb_matrix_set_color(led_index, rgb.r, rgb.g, rgb.b);
            } else {
                rgb_matrix_set_color(led_index, RGB_WHITE);  // steady once connected
            }
        }

        led_index = g_led_config.matrix_co[1][3];  // BLE3 active/pairing?
        if (led_index != NO_LED && Keyboard_Info.Key_Mode == QMK_BLE_MODE
            && Keyboard_Info.Ble_Channel == QMK_BLE_CHANNEL_3) {
            if (Keyboard_Status.System_Connect_Status == KB_MODE_CONNECT_PAIR) {
                uint8_t breath = sin8(timer_read() >> 2);

        led_index = g_led_config.matrix_co[1][4];  // 2.4G active/pairing?
        if (led_index != NO_LED && Keyboard_Info.Key_Mode == QMK_2P4G_MODE) {
            if (Keyboard_Status.System_Connect_Status == KB_MODE_CONNECT_PAIR) {

            } else {
                rgb_matrix_set_color(led_index, RGB_WHITE); // steady once connected
            }
        }

        // Battery level, above BAT: 5-segment bar, cols 7-11, each segment
        // is 20%.  This reuses the existing HS_* palette with only orange
        // (warning <= 20%) and otherwise green.
        static const uint8_t PROGMEM batt_seg_col[5] = {7, 8, 9, 10, 11};
        static const uint8_t PROGMEM batt_seg_hs[5][2] = {
            {HS_ORANGE},  // The sole warning light
            {HS_GREEN},   // Green for the remainder, which is nice (no bleed)
            {HS_GREEN},
            {HS_GREEN},
            {HS_GREEN},
        };
        uint8_t pct = Keyboard_Info.Batt_Number;

        uint8_t lit = (pct == 0) ? 0 : ((pct + 19) / 20);  // ceiling: 1-5 segments
        if (lit > 5) lit = 5;

        for (uint8_t i = 0; i < 5; i++) {
            if (i >= lit) continue;                         // unlit segment stays off
            uint8_t col = pgm_read_byte(&batt_seg_col[i]);
            uint8_t h   = pgm_read_byte(&batt_seg_hs[i][0]);
            uint8_t s   = pgm_read_byte(&batt_seg_hs[i][1]);
            led_index = g_led_config.matrix_co[1][col];
            if (led_index != NO_LED) {
                HSV hsv = {h, s, rgb_matrix_get_val()};
                RGB rgb = hsv_to_rgb(hsv);
                rgb_matrix_set_color(led_index, rgb.r, rgb.g, rgb.b);

    }

    // Base layer
    if (layer == 0) {
        static const uint8_t PROGMEM base_hues[][3] = {
