[#amplefirmwarememory]
=== Ample firmware memory

Unlike my KPRepublic BM40’s ATmega32U4, the memory cost of per-key,
brightness-reactive RGB lighting is incidental on the CSTC40 given its
STM32F402RCT6 MCU, which has 256 kB of flash memory.  That is revealed by
`INFO_UF2.TXT`, which appears on the “drive”, which appears when the CSTC40 is
put into bootloader mode.

....
TinyUF2 Bootloader 0.18.2-35-g730f3c2-dirty - tinyusb (0.16.0-783-gd10b65ada)
Model: FXTwink FXTwink
Board-ID: FXTwink
Date: May 31 2024
Flash Size: 0x00040000 bytes
....

Consequently, no features _must_ be disabled.  However, some are because I:

1. Want to keep my 40% keyboards consistent, and
2. Do not want several features, including:

* CAPS_WORD_ENABLE
* GRAVE_ESC_ENABLE
* LAYER_LOCK_ENABLE
* MAGIC_ENABLE
* REPEAT_KEY_ENABLE

Those are discussed in detail at
<<keymapskennypeterulesmkamendments,keymaps/kennypete/rules.mk amendments>>.

[#startingpoint]
=== Starting point

This board builds from mainline qmk_firmware, and my work here primarily is
configuration and delivering feature-parity.  That is, bringing an
already-current, working source in line with my other boards, rather than
fixing defects in it.

EXTRAKEY_ENABLE         RAW_ENABLE              TAP_DANCE_ENABLE        WEAR_LEVELING_ENABLE
----

Some of these features are mandatory.

1. `EEPROM_ENABLE` is compiled in by default on any board.  `EEPROM_DRIVER`
defaults to `vendor` (`qmk_firmware/builddefs/common_features.mk`, line 173).
For the CSTC40’s STM32 chip, `vendor` is itself a smart per-platform selector
automatically resolving to `wear_leveling`, which in turn automatically sets
`WEAR_LEVELING_DRIVER ?= embedded_flash` in the same block (lines 210-226),
enabling `WEAR_LEVELING_ENABLE` and `FNV_ENABLE`.footnote:[Regarding `FNV_ENABLE`, it has no dedicated QMK documentation.  It is an internal flag for the Fowler-Noll-Vo hash algorithm, used for integrity-checking by QMK’s wear-leveling EEPROM emulation in `qmk_firmware/builddefs/common_features.mk`.]
2. `qmk_firmware/builddefs/common_features.mk` also dictates other mandatory
settings for any keyboard with `VIA_ENABLE`, which Vial requires.  Those
settings are `BOOTMAGIC_ENABLE`, `DYNAMIC_KEYMAP_ENABLE`, `RAW_ENABLE`, and
`TRI_LAYER_ENABLE`.

Other settings are discussed at
<<keyboardjsonamendments,keyboard.json amendments>>
(i.e., `MOUSEKEY_ENABLE`, `EXTRAKEY_ENABLE`, and `RGB_MATRIX_ENABLE`, plus
their knock-on features, `MOUSE_ENABLE` and `SHARED_EP_ENABLE`), and the
remainder are discussed at
<<keymapskennypeterulesmkamendments,keymaps/kennypete/rules.mk amendments>>.

The following files provide the default QMK/Vial setup for the CSTC40 rev3:

The command line used here points to the complicated directory structure due to
the CSTC40’s multiple revisions, daughterboard, and single_pcb variants.

For my purposes in the `kennypete` build, the structure is normalised to handle
only my rev3, aligning to my BM40’s directory and files utilised.

The `kennypete` QMK/Vial setup for the CSTC40 rev3 is:

ifdef::env-codeberg[&#x00A0; ]

[source,shell-session]
----
[~/qmk_firmware/keyboards/kprepublic/cstc40/rev3] $ shopt -s globstar extglob
[~/qmk_firmware/keyboards/kprepublic/cstc40/rev3] $ ls -R --width=15 **/*.@(c|json|h|mk)
keyboard.json
keymaps/kennypete/config.h
keymaps/kennypete/keymap.c
keymaps/kennypete/rules.mk
keymaps/kennypete/vial.json
----

* All files in the `vial` directory plus the `keyboard.json` are amended,
as explained below.
* The relevant content of `info.json` is assimilated into `keyboard.json`.
* The `vial` directory is renamed `kennypete`.
* The final, compilation output is included below – see
<<compilation,Compilation>>.
* The resulting compiled file is `kprepublic_cstc40_rev3_kennypete.uf2`,
which is flashed to the board by copying that file to the “drive” that appears
in File Explorer when the physical key at position (0,0) is held while plugging
in the keyboard (i.e., bootmagic reset).

Note: The files `config.h`, `halconf.h` and `mcuconf.h` were found to be
redundant for the rev3 because it uses ws2812, a different, non-I2C protocol.

The `vial` folder is renamed for a couple of reasons.  First, its contents are
extensively updated.  Second, albeit incidentally, when named `vial`, the `qmk
lint` check fails, whereas when it is named `kennypete`:

ifdef::env-codeberg[&#x00A0; ]

[source,shell-session]
----
[~/qmk_firmware] $ qmk lint -kb kprepublic/cstc40/rev3 -km kennypete
Ψ Lint check passed!
----

[#keyboardjsonamendments]
==== keyboard.json amendments

The stock’s `info.json` is merged into `rev3/keyboard.json` defining the board
itself, i.e., matrix pins, the WS2812 driver declaration (`"driver": "ws2812"`,
pin `B13`), USB IDs, which QMK features are available by default, and the RGB
Matrix hardware layout.  Anything set here is the fallback every keymap on this
board inherits (unless it overrides it at the keymap level).  Changes made:

* `nkro` is changed from "true" to "false", matching the BM40/to be
consistent with the other boards (and I have no need for the feature being
enabled).
* `rgb_matrix.animations` list is reduced from 48 available effects down to
just three (`cycle_all`, `cycle_left_right`, and `hue_pendulum`).  As I have no
desire for any more than a few animations, usually preferring “Direct Control”
with my per-key solid colours, this is done for personal preference and
alignment (rather than for a space-saving purpose).

[NOTE]
====
This file’s `features` block also sets `mousekey`, `extrakey`, and
`rgb_matrix` to true, which are not just incidental for my setup because the:

* mouse keys on Layer 5 depend on `mousekey` being enabled,
* the media/volume row requires `extrakey`, and
* the per-key RGB system needs `rgb_matrix`.

These three enabled settings then cascade (forced by QMK core code), setting:

* `MOUSEKEY_ENABLE = true`, which sets `MOUSE_ENABLE` as
enabled (in `builddefs/common_features.mk`)
* `MOUSE_ENABLE` and `EXTRAKEY_ENABLE` each independently
force `SHARED_EP_ENABLE` on (in `tmk_core/protocol.mk`).
====

The other change is adding an alias for "LAYOUT_planck_mit":

ifdef::env-codeberg[&#x00A0; ]

[source,json]
----
    "layout_aliases": {
        "LAYOUT_planck_mit": "LAYOUT_ortho_4x12_1x2uC",
----

This enables using "LAYOUT_ortho_4x12_1x2uC" later in
<<filerev3keymapskennypetekeymapc,keymap.c>>, aligning that file with the
BM40’s one.

[#keymapskennypeteconfighamendments]
==== keymaps/kennypete/config.h amendments

The `keymaps/{keymap}/config.h` contains settings specific to the keymap, i.e.,
Vial’s unique board identifier and unlock key combination, how many layers
Vial’s dynamic keymap supports, and so on.

ifdef::env-codeberg[&#x00A0; ]

[cols="4,7"]
|===
^.^m|VIAL_UNLOCK_COMBO_ROWS
<.^|The unlock keys’ rows are standardised to the BM40’s (i.e., 0 and 2).
^.^m|DYNAMIC_KEYMAP_LAYER_COUNT
<.^|This is reduced from `10` to `7` because I currently only use six layers,
am very unlikely to ever want more than one more, and it makes it consistent
with my other keyboards (particularly the BM40 where space limits mean having
more than seven layers is impracticable).
^.^m|DYNAMIC_KEYMAP_MACRO_COUNT
<.^|Set to `3` because I only use one macro (and even that is trivial).  So, I
do not expect either to need, or to add, more.
^.^m|VIAL_COMBO_ENTRIES
<.^|Set to `6`.  I have three currently and may add a few more at some point.
So, providing for another three is enough.
^.^m|VIAL_KEY_OVERRIDE_ENTRIES
<.^| Set to `6`.  I have three currently and may find the need for some more,
though three should be enough.
^.^m|VIAL_TAP_DANCE_ENTRIES
<.^|Set to `9` (reduced from `32`); I use seven, though am unlikely to add
many more, with current usage focused on layer movement and locking things like
Num and Scoll lock.
^.^m|NO_ACTION_ONESHOT
<.^|On the BM40 this is a space saver delivered with no cost to me given I do
not use one shot modifiers.  It is included in the CSTC40 for consistency.
^.^m|MOUSEKEY&#x002A;
<.^|Several settings are added, which deliver my preferences for the mouse
keys’ timings.
|===

[#keymapskennypeterulesmkamendments]
==== keymaps/kennypete/rules.mk amendments

The <<filerev3keymapskennypeterulesmk,rules.mk>> file controls which QMK
features get compiled into the firmware (except when overridden at a higher
level, which can include QMK determinations, not just keyboard-specific ones).
The CSTC’s default file sets `TRI_LAYER_ENABLE`, `VIA_ENABLE`, `VIAL_ENABLE`,
`VIALRGB_ENABLE`, and `TAP_DANCE_ENABLE` to “yes” and no settings to “no”.  The
entire file is replaced with the one used with the BM40 except:

* `AVR_USE_MINIMAL_PRINTF = yes` is omitted since it is an AVR-only setting,
inapplicable to the CSTC40’s STM32 MCU.
* `LTO_ENABLE` is changed to “no” because it trims back other features that
are otherwise automatically enabled.

ifdef::env-codeberg[&#x00A0; ]

Otherwise, the alignment provides for a consistent experience across my
40&#x0025; keyboards.

[NOTE]
====
* `"processor": "STM32F401"` is correct as written, despite the actual MCU
being an STM32F402RCT6 (confirmed both via `rev3/readme.md` and directly from
the board’s own `INFO_UF2.TXT` reporting a 256&#x00A0;kB flash size matching
that part).
* QMK's `info.json` schema has a fixed, closed list of accepted `processor`
values that does not include `STM32F402`.  The nearest QMK-recognised build
target is `STM32F401` and the two chips share close enough register/peripheral
compatibility that building against it works correctly.
====

static void apply_hsv_table(const uint8_t (*table)[3], uint8_t count) {
    uint8_t val = rgb_matrix_get_val();  // live global brightness

    for (uint8_t i = 0; i < count; i++) {
        uint8_t rc  = pgm_read_byte(&table[i][0]);
        uint8_t h   = pgm_read_byte(&table[i][1]);
        uint8_t s   = pgm_read_byte(&table[i][2]);
        uint8_t row = rc >> 4;
        uint8_t col = rc & 0x0F;

        HSV hsv = {h, s, val};
        RGB rgb = hsv_to_rgb(hsv);

        uint8_t led_index = g_led_config.matrix_co[row][col];
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, rgb.r, rgb.g, rgb.b);
        }
    }
}

static void apply_off_table(const uint8_t *table, uint8_t count) {
    for (uint8_t i = 0; i < count; i++) {
        uint8_t rc  = pgm_read_byte(&table[i]);
        uint8_t row = rc >> 4;
        uint8_t col = rc & 0x0F;
        uint8_t led_index = g_led_config.matrix_co[row][col];
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_OFF);
        }
    }
}

// Hue, Sat pairs for colour names
//
// QMK's RGB Matrix works in HSV internally, scaled 0-255 for all three of
// H/S/V (not the usual 0-360 degrees / 0-100% you'd see in a colour picker).
// Only H and S are stored here; V comes from the current brightness at
// render time, which is what makes these colours respond to Bright +/-.
//
// RGB->HSV conversion, worked for all three possible "max channel" cases
// (the hue formula changes depending on which of R/G/B is largest):
//
// R is max -- "MAGENTA" RGB (255, 0, 126):
//   max=255 (Red), min=0, delta=255
//   S = 255 * (delta/max) = 255 * (255/255) = 255
//   H = 60 * ((G-B)/delta) = 60 * ((0-126)/255) = -29.65 deg
//   Negative result -- wrap by adding 360: -29.65 + 360 = 330.35 deg
//   H rescaled to QMK's 0-255: round(330.35 * 255/360) = 234
//   -> HS_MAGENTA = 234, 255
//
// G is max -- "GREEN" RGB (0, 255, 0):
//   max=255 (Green), min=0, delta=255
//   S = 255 * (delta/max) = 255 * (255/255) = 255
//   H = 60 * (((B-R)/delta) + 2) = 60 * (((0-0)/255) + 2) = 120 deg
//   H rescaled to QMK's 0-255: round(120 * 255/360) = 85
//   -> HS_GREEN = 85, 255
//
// B is max -- "ROYAL" RGB (83, 184, 255):
//   max=255 (Blue), min=83, delta=172              <- not fully saturated;
//                                                      min isn't 0 here
//   S = 255 * (delta/max) = 255 * (172/255) = 172
//   H = 60 * (((R-G)/delta) + 4) = 60 * (((83-184)/172) + 4) = 204.77 deg
//   H rescaled to QMK's 0-255: round(204.77 * 255/360) = 145
//   -> HS_ROYAL = 145, 172
//
// V (brightness) is always just the max channel itself, unscaled -- but it's
// deliberately not stored in these pairs, since it comes live from the
// board's current brightness setting instead (see apply_hsv_table above).
//
// Hue, Sat pairs for the built-in RGB_* colours (quantum/colors.h) with
// lime bespoke to ensure it is visually distinct and not quasi white
#define HS_WHITE     0,   0
#define HS_ROSE      0,   90
#define HS_RED       0,   255
#define HS_ORANGE    24,  150

=== Flash

Flashing is done by copying the generated
`kprepublic_cstc40_rev3_kennypete.uf2` file to the “drive” that appears in File
Explorer when the board is in bootmagic reset mode (holding key 0,0 and
plugging in the keyboard).
