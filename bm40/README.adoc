[#workingwithalimitedfirmwaresizeceiling]
=== Working with a limited firmware size ceiling

A critical issue with the BM40 is that, as shipped, the default build’s `.hex`
file leaves very little free space – so much so that, if it is left in its
“stock” setup, adding per-key RGB would exceed the 28,672&#x00A0;bytes
available on the BM40’s ATmega32U4 MCU.

ifdef::env-codeberg[&#x00A0; ]

Specifically, the compiled default Vial build
(`keyboards/kprepublic/bm40hsrgb/rev2/keymaps/vial`) leaves 2,428 bytes of free
space.  As the memory cost of per-key, brightness-reactive RGB lighting is not
trivial, other feature(s) must be disabled.  This is especially the case
because I also want `VIALRGB_ENABLE` and `TAP_DANCE_ENABLE`, both of which are
not enabled in the stock.

ifdef::env-codeberg[&#x00A0; ]

Fortunately, I do not use/want several features, which are inherently included
in the stock build, and which collectively “free” around 3 kB:

* CAPS_WORD_ENABLE
* GRAVE_ESC_ENABLE
* LAYER_LOCK_ENABLE
* MAGIC_ENABLE
* REPEAT_KEY_ENABLE

Those are discussed in detail at
<<keymapskennypeterulesmkamendments,keymaps/kennypete/rules.mk amendments>>.

ifdef::env-codeberg[&#x00A0; ]

A further &gt;1&#x00A0;kB is saved by purging most of the stock’s RGB Matrix
animations, which is a recommended https://docs.qmk.fm/squeezing_avr[squeezing]
technique.

NOTE: It is also critical not to enable
https://get.vial.today/docs/firmware-size.html#qmk-settings[`QMK_SETTINGS`],
which would add around 5 kB, an impracticable cost.  Vial itself defaults
`QMK_SETTINGS` to “yes” (in `builddefs/build_vial.mk`) both the stock and this
setup explicitly override that back to “no”.

[NOTE]
====
Unlike the Geonix (1152-byte EEPROM), the BM40’s ATmega32U4 has only 1024 bytes
to work with.  Further, combo/key-override entries share one pool with QMK’s
enforced 100-byte reservation for macros.  Working through the actual address
arithmetic (`quantum/nvm/eeprom/nvm_dynamic_keymap.c`): the fixed cost of seven
layers, nine tap dances, and the VIA/eeconfig header leaves exactly 120
bytesfootnote:[The usable range, `DYNAMIC_KEYMAP_EEPROM_MAX_ADDR`, defaults to `TOTAL_EEPROM_BYTE_COUNT - 1` when not overridden (confirmed in `quantum/nvm/eeprom/nvm_dynamic_keymap.c`).  For the ATmega32U4, `TOTAL_EEPROM_BYTE_COUNT` is a hardcoded 1024 (per-chip, in `platforms/eeprom.h`), not a user-set `EEPROM_SIZE`, which only applies to other EEPROM driver types.  This gives 1023, one less than 1024, due to zero indexing.]
free before that reservation.  That is a combined ceiling of 12 combo {plus}
key-override entries.  My `6 + 6` sits precisely at that limit, confirmed by a
clean compile with no headroom left in that specific pool.  Any further combo
or override would need either a larger EEPROM, or trimming elsewhere (most
effectively layers, at &#x007E;96 bytes each is far costlier per unit than
combo/key-override’s 10 bytes each).
====

[#keyboardjsonamendments]
==== keyboard.json amendments

The file <<filerev2keyboardjson,keyboard.json>> defines the board itself, i.e.,
matrix pins, USB IDs, which QMK features are available by default, and the RGB
Matrix hardware layout.  Anything set here is the fallback every keymap on this
board inherits (unless it overrides it at the keymap level).  Changes made:

* `rgblight` (incorrectly, `true`), `tri_layer`, and `build.lto`
are removed because, as `qmk info -kb kprepublic/bm40hsrgb/rev2 -km vial`
revealed, they are specified already in `rules.mk`, and the latter “wins”.
* The `ws2812` pin block is removed because the
BM40’s `rgb_matrix.driver` is `is31fl3733`, an I2C-based chip that has no use
for a WS2812 pin declaration.
* `rgb_matrix.animations` list is reduced from 38 available animations
down to just three (`cycle_all`, `cycle_left_right`, and `hue_pendulum`).  Each
unused effect comes with a memory cost, regardless of whether it is ever
selected/wanted, so this is an easy trade of too many animation choices for
flash headroom.  And as I have no desire for any more than a few animations,
usually preferring “Direct Control” and my per-key solid colours.

[NOTE]
====
This file’s `features` block also sets `mousekey`, `extrakey`, and `rgb_matrix`
to true, which are not just incidental for my setup because the:

* mouse keys on Layer 5 depend on `mousekey` being enabled,
* the media/volume row requires `extrakey`, and
* the per-key RGB system needs `rgb_matrix`.

These three enabled settings then cascade (forced by QMK core code), setting:

* `MOUSEKEY_ENABLE = true`, which sets `MOUSE_ENABLE` as enabled (in
`builddefs/common_features.mk`)
* `MOUSE_ENABLE` and `EXTRAKEY_ENABLE` each independently force
`SHARED_EP_ENABLE` on (in `tmk_core/protocol.mk`).
====

The `MOUSEKEY*` settings _could_ be set by making them available within Vial.

it contains “facts” about the board itself, not my preferences).

[#keymapskennypetekeymapcamendments]
==== keymaps/kennypete/keymap.c amendments

As its filename suggests, <<filerev2keymapskennypetekeymapc,keymap.c>> contains
QMK’s keymap for the board when it is compiled.  However, because I use Vial
for storing the final working layout (i.e., dynamically in the keyboard’s
EEPROM), the `keymaps[]` array in `keymap.c` is only ever used as a temporal,
initially-flashed state prior to reloading my complete keymap using a saved
`.vil` file.  I like this approach because I detest the commonly weird setups
usually delivered with stock `keymap.c` files.  As it is a fallback too (should
the EEPROM state ever be wiped) the file is updated from the default as
follows:

* *Layers*: These are changed from the default by amending
layer 0 (`_BASE`) a little to mostly match the final Vial setup’s arrangement:
** Layer 1 (`_SYMBOLS`) is limited to symbols, arrow keys on HJKL, kbd:[F1] to
kbd:[F12], and kbd:[&#x005F;], kbd:[&#x002B;], kbd:[{], kbd:[}],
kbd:[&#x007C;], and kbd:[.].
** Layer 2 (`_NUMBERS`) is limited to numbers, arrow keys on HJKL, plus
kbd:[-], kbd:[=], kbd:[&#x005B;], kbd:[&#x005D;], and kbd:[&#x002B;].
** Layer 3 (`_ADJUST`) is a bootloader key-only layer.
** There is neither layer 4 nor layer 5 defined because they are superfluous
for the basic, default state.  Those two layers are set only in the Vial setup,
which is loaded after flashing the firmware.
+
[NOTE]
====
The result is a much more congruous default-to-final layout.  This is useful,
for me at least, because it means common typing tasks before the Vial file is
loaded can be performed.  For example, the kbd:[Ctrl] key is at R3C0 (where I
always want it) whereas, in KPRepublic’s original keymap that position is
`RGB_TOG` (_WTH?_).  There is some inherent deception here, though.  Per-key
colour-wise, many keys on layers 1 and 2 are `KC_NO` rather than their final
state.  That has no meaningful consequence, however.
====

* *Per-key colours*: The function `rgb_matrix_indicators_user()`,
together with support functions `apply_hsv_table()` and `apply_off_table()`,
check which layer is currently active and, for every key that should show a
fixed colour, looks up that key’s physical LED and sets it directly.  In doing
so, that overrides whatever the board’s selected background effect would be
otherwise.
** _Colours_ are stored as compact hue/saturation pairs (i.e., not full RGB
triples) using 14 `#define HS_*` definitions.  Consequently, those are added to
flash memory (rather than EEPROM), and row/column positions are packed into a
single byte each via a small `RC(row, col)` macro, which keeps the memory cost
low.
** _Brightness_ is not stored per colour, deliberately.  It is read live from
the board’s current brightness setting every time a colour is drawn, which is
what makes every one of these fixed colours brighten, responding to
user-adjustment (Bright{plus}, `RGB_VAI`) and a key override to reduce
brightness when shifted.  The exception to this is Layer 3’s `QK_BOOT` key,
which, along with the held Lower-Upper keys, is intentionally hard-coded to a
fixed, non-scaling red.  That is appropriate given the `QK_BOOT` key’s use
case, with the colour a kind of “safety indicator”, always visible regardless
of the general brightness setting.
+
NOTE: The final presentation of this RGB per-key setup is shown in the six
photos at <<keyboardphotos,Keyboard photos>>.

[#keymapskennypetevialjsonamendments]
==== keymaps/kennypete/vial.json amendments

The file <<filerev2keymapskennypetevialjson,vial.json>> is Vial’s descriptor
for the board, including physical key layout, matrix dimensions, and it also
determines which optional Vial-specific GUI features to expose.  The change
made to the file are to align it with the CSTC40’s file, which is optimal on
two counts.  Consequently:

1. The following VIA-only
metadatafootnote:[“`name`, `vendorId`, `productId`: while these options are required by VIA, Vial does not need them. You do not have to add them, and even if you do, their contents will not be used.” - https://get.vial.today/docs/porting-to-via.html#2-create-a-json-containing-the-full-keyboard-definition]

regardless):
+
[source,json]
----
    "name": "bm40v2",
    "vendorId": "0x4B50",

----

2. `"lighting": ["qmk_lighting"],` is changed to:
+
[source,json]
----
    "lighting": "vialrgb",
----

This is a separate setting to <<filerev2keymapskennypeterulesmk,rules.mk>>’s
`VIALRGB_ENABLE = yes`, which compiles the capability into the firmware.  The
Vial application only renders the “Lighting” tab if this descriptor also
explicitly declares which lighting protocol to use.  Without both the
`VIALRGB_ENABLE` setting and this change to the `"lighting"` line, the Lighting
tab does not appear.

[#layer2raise]
==== Layer 2 (Raise)

image:https://i.postimg.cc/cCxVh2Nx/all-layer2.jpg[Vial_L2,width=535]

* This layer’s top row is backtick and the digit keys.
R1C10, R1C11, and R2C8 to R2C10 have the unshifted versions of kbd:[-],
kbd:[=], kbd:[&#x005B;], kbd:[&#x005D;], and kbd:[&#x005C;].  Specific,
significant features:
** The same group of five keys as on layer 1 at the “L” from
<<layer1lower,R1C0 to R3C2>>.
** The kbd:[Ctrl]-modified kbd:[F1] to kbd:[F12] keys, which are used to
provide more options at the OS and application level because, at the OS level
especially, a control modified function at/below kbd:[F12], although rare, will
be recognised.  (Conversely, although kbd:[F13] to kbd:[F24] function keys look
like a good idea, often they aren’t recognised.)
** The 2U key, which has `LCS` (kbd:[Ctrl]{plus}kbd:[Shift]) kbd:[F12].  This
is a Vim-targeted key, which is mapped (in my Vim `.vimrc`, for Command-line
and Insert modes) to the non-breaking space (U{plus}00A0, decimal 160) with:
+
[source,vim]
----
cnoremap <S-C-F12> <Char-160>
inoremap <S-C-F12> <Char-160>
----

[#layer3bootloaderonly]
==== Layer 3 (Bootloader only)

image:https://i.postimg.cc/8cZx0411/bm40-cstc40-layer3.jpg[Vial_L3,width=535]

Intentionally, this is almost an empty layer.  The reason is driven by my
Planck Ez.  It has a mandatory “Adjust” layer, which is layer 3.  Leveraging
that, given it is sometimes awkward to hold those keys together as well as
strike another key, where it _is_ useful is when you have something(s) that you
want to be difficult to access (or will rarely want to use, which is where it
is utilised on my Geonix Rev.2.5 for battery indicator and input
selection/indication).  So, it is retained, but only with `QK_BOOT` at R0C4,
turning what I may otherwise consider an annoyance into a feature.

[#layer4numpad]
==== Layer 4 (Numpad)

image:https://i.postimg.cc/Vvf3gpcY/all-layer4.jpg[Vial_L4,width=535]

* This number pad layer is accessed from either layer 0 or layer 5 with a
double tap of R3C3.  Returning to layer 0 is achieved with a tap of the same
key (which behaves identically, being the transparent key to `TD(2)`).  So,
this layer, and layer 5, are different in that they are “on” indefinitely
whereas layers 1, 2, and 3 are active only momentarily while the Lower and/or
Raise key(s) are held.
+
[NOTE]
====
A physical 5-row keyboard is needed to mimic something closer to a “normal”
number pad, so this is a bespoke pad.  That said, the per-key RGB, combined
with the nub on kbd:[5] (located where the QWERTY “J” is at R1C6), makes it
similar enough.  The only macro on this board, `M0`, is on the 2U key.  It
delivers two zeros (sometimes seen on number pads).
====
* The “WASD” keys are used to provide a cursor movement option given my usual,
preferred, “HJKL” are otherwise occupied, and
* Being right-handed, for me a number pad needs to be on the RHS to make sense.


[#layer5adjust]
==== Layer 5 (“Adjust”)

image:https://i.postimg.cc/nrF62gt9/all-layer5.jpg[Vial_L5,width=535]

* This is the “real” adjustment layer. It is accessed from either layer 0 or
layer 4 by holding R3C3.  Returning to layer 0 is achieved with a tap of the
same key (which behaves identically, being the transparent key to `TD(2)`).
Points of note:
** Many positions, including R0C0 to R0C9, are intentionally `KC_NO`, either
for future use or as helpful separators when looking at the backlighting.
** Everything else broadly is self-explanatory.

#define RC(r, c) (((r) << 4) | (c))

static void apply_hsv_table(const uint8_t (*table)[3], uint8_t count) {
    uint8_t val = rgb_matrix_get_val();  // live global brightness

    for (uint8_t i = 0; i < count; i++) {
        uint8_t rc  = pgm_read_byte(&table[i][0]);
        uint8_t h   = pgm_read_byte(&table[i][1]);
        uint8_t s   = pgm_read_byte(&table[i][2]);
        uint8_t row = rc >> 4;
        uint8_t col = rc & 0x0F;

        HSV hsv = {h, s, val};
        RGB rgb = hsv_to_rgb(hsv);

        uint8_t led_index = g_led_config.matrix_co[row][col];
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, rgb.r, rgb.g, rgb.b);
        }
    }
}

static void apply_off_table(const uint8_t *table, uint8_t count) {
    for (uint8_t i = 0; i < count; i++) {
        uint8_t rc  = pgm_read_byte(&table[i]);
        uint8_t row = rc >> 4;
        uint8_t col = rc & 0x0F;
        uint8_t led_index = g_led_config.matrix_co[row][col];
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_OFF);
        }
    }
}

// Hue, Sat pairs for colour names
//
// QMK's RGB Matrix works in HSV internally, scaled 0-255 for all three of
// H/S/V (not the usual 0-360 degrees / 0-100% you'd see in a colour picker).
// Only H and S are stored here; V comes from the current brightness at
// render time, which is what makes these colours respond to Bright +/-.
//
// RGB->HSV conversion, worked for all three possible "max channel" cases
// (the hue formula changes depending on which of R/G/B is largest):
//
// R is max -- "MAGENTA" RGB (255, 0, 126):
//   max=255 (Red), min=0, delta=255
//   S = 255 * (delta/max) = 255 * (255/255) = 255
//   H = 60 * ((G-B)/delta) = 60 * ((0-126)/255) = -29.65 deg
//   Negative result -- wrap by adding 360: -29.65 + 360 = 330.35 deg
//   H rescaled to QMK's 0-255: round(330.35 * 255/360) = 234
//   -> HS_MAGENTA = 234, 255
//
// G is max -- "GREEN" RGB (0, 255, 0):
//   max=255 (Green), min=0, delta=255
//   S = 255 * (delta/max) = 255 * (255/255) = 255
//   H = 60 * (((B-R)/delta) + 2) = 60 * (((0-0)/255) + 2) = 120 deg
//   H rescaled to QMK's 0-255: round(120 * 255/360) = 85
//   -> HS_GREEN = 85, 255
//
// B is max -- "ROYAL" RGB (83, 184, 255):
//   max=255 (Blue), min=83, delta=172              <- not fully saturated;
//                                                      min isn't 0 here
//   S = 255 * (delta/max) = 255 * (172/255) = 172
//   H = 60 * (((R-G)/delta) + 4) = 60 * (((83-184)/172) + 4) = 204.77 deg
//   H rescaled to QMK's 0-255: round(204.77 * 255/360) = 145
//   -> HS_ROYAL = 145, 172
//
// V (brightness) is always just the max channel itself, unscaled -- but it's
// deliberately not stored in these pairs, since it comes live from the
// board's current brightness setting instead (see apply_hsv_table above).
//
// Hue, Sat pairs for the built-in RGB_* colours (quantum/colors.h) with
// lime bespoke to ensure it is visually distinct and not quasi white
#define HS_WHITE     0,   0
#define HS_ROSE      0,   90
#define HS_RED       0,   255
#define HS_ORANGE    24,  150
#define HS_YELLOW    42,  255
#define HS_LIME      68,  167
#define HS_GREEN     85,  255
#define HS_EMERALD   107, 255
#define HS_CYAN      128, 255
#define HS_ROYAL     145, 172
#define HS_BLUE      170, 255

#define HS_MAGENTA   234, 255

bool rgb_matrix_indicators_user(void) {
    uint8_t layer = get_highest_layer(layer_state);

    // Special treatment of layer three, which has only the QK_BOOT key
    // (keeping fixed-brightness deliberately as a safety indicator, not part
    // of the colour scheme).  The QK_BOOT key and the Lower/Raise keys are
    // all made RGB_RED so that it is really clear we are in a danger zone.
    if (layer == 3) {
        rgb_matrix_set_color_all(RGB_OFF);

        uint8_t led_index = g_led_config.matrix_co[0][4];   // QK_BOOT
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_RED);
        }

        led_index = g_led_config.matrix_co[3][4];            // Lower, is being held
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_RED);
        }

        led_index = g_led_config.matrix_co[3][7];            // Raise, is being held
        if (led_index != NO_LED) {
            rgb_matrix_set_color(led_index, RGB_RED);
        }

        return false;
    }

    // Base layer
    if (layer == 0) {
        static const uint8_t PROGMEM base_hues[][3] = {
            // Default for alpha characters and punctuation so that a couple
            // of RGB modes (Cycle Left Right and Hue Pendulum) can be used
            // Row 0 just ` as BLUE and Backspace RED
            {RC(0,0), HS_YELLOW},   // Tab
            {RC(0,11), HS_RED},     // Bksp
                                    // Other 1-10 Q W E R T Y U I O P default
            // Row 1
            {RC(1,0), HS_GREEN},    // Esc
            {RC(1,4), HS_YELLOW},   // F
            {RC(1,7), HS_YELLOW},   // J
                                    // Other 1-3,5,6,8-11 A S D G H K L ; ' default
            // Row 2
            {RC(2,0), HS_ROSE},     // Sft
                                    // 1-10 Z X C V B N M , . / default
            {RC(2,11), HS_ROSE},    // RS Enter
            // Row 3
            {RC(3,0), HS_ROSE},     // Ctl
            {RC(3,1), HS_PURPLE},   // TD(3) - Gui [Hold: Gui; Double Tap: Gui+E]
            {RC(3,2), HS_MAGENTA},  // Alt
            {RC(3,3), HS_BLUE},     // TD(2) - TO(0) [Double Tap: TO(4); Hold: TO(5)]
            {RC(3,4), HS_ROSE},     // Lower
                                    // (3,5) space default
                                    // (3,6) is n/a for this 2U board
            {RC(3,7), HS_ROSE},     // Raise
            {RC(3,8), HS_ROYAL},    // Home [Hold: Meh (Ctl + Sft + Alt)]
            {RC(3,9), HS_BLUE},     // Mouse Wheel Down [Hold: Hyper (Ctl + Sft + Alt + Gui)]
            {RC(3,10), HS_PURPLE},  // Mouse Wheel Up [Hold: Gui]
            {RC(3,11), HS_PURPLE},  // End [Hold: Ctl]
        };
        apply_hsv_table(base_hues, ARRAY_SIZE(base_hues));
        return false;
    }

    // Lower layer
    if (layer == 1) {
        static const uint8_t PROGMEM lower_hues[][3] = {
            // Row 0
            {RC(0,0), HS_ROYAL},    // ~
            {RC(0,1), HS_ROYAL},    // !
            {RC(0,2), HS_ROYAL},    // @
            {RC(0,3), HS_ROYAL},    // #
            {RC(0,4), HS_ROYAL},    // $
            {RC(0,5), HS_ROYAL},    // %
            {RC(0,6), HS_ROYAL},    // ^
            {RC(0,7), HS_ROYAL},    // &
            {RC(0,8), HS_ROYAL},    // *
            {RC(0,9), HS_ROYAL},    // (
            {RC(0,10), HS_ROYAL},   // )
            {RC(0,11), HS_RED},     // Delete
            // Row 1
            {RC(1,0), HS_ROSE},     // TD(4) - NO [Double Tap: Caps Lock]
            {RC(1,1), HS_EMERALD},  // F1
            {RC(1,2), HS_EMERALD},  // F2
            {RC(1,3), HS_EMERALD},  // F3
            {RC(1,4), HS_EMERALD},  // F4
            {RC(1,5), HS_EMERALD},  // F5
            {RC(1,6), HS_YELLOW},   // Left
            {RC(1,7), HS_YELLOW},   // Down
            {RC(1,8), HS_YELLOW},   // Up
            {RC(1,9), HS_YELLOW},   // Right
            {RC(1,10), HS_ROYAL},   // _

            // Row 2

            {RC(2,7), HS_EMERALD},  // F12
